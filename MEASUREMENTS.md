# Measurements

Every figure in the README comes from this file, and every figure here comes
from a file under [`results/`](results). Runs were made on 2026-10-13.

## Environment

| | |
|---|---|
| Host | Apple M5 (4 performance + 6 efficiency cores), 24 GiB, macOS 27.0.1 |
| Docker | Docker Desktop 29.8.2, Linux VM with 8 CPUs and 11.67 GiB, aarch64 |
| Citus | 14.2.0 on PostgreSQL 17.11, **built from the `v14.2.0` source tag** on `postgres:17-bookworm` (the published Citus images are amd64-only); image `sha256:f87955bf…` |
| TimescaleDB | 2.30.2 on PostgreSQL 17.11, `timescale/timescaledb@sha256:b346edcd…`, Timescale License edition |
| ClickHouse | 25.8.33.6 server and Keeper, `clickhouse/clickhouse-server@sha256:0152dd51…`, `clickhouse/clickhouse-keeper@sha256:86ef98ab…` |
| Client | Python 3.12 benchmark container on each compose network ([`tools/Dockerfile`](tools/Dockerfile)) |

**The host was not quiet.** The 1-minute load average sat between 10 and 44
during the runs (each `results/*/environment.txt` and the rebalance's
`rebalance-host-load.txt` record it). A network-filtering system extension on
this machine used up to ~245% CPU, and 13 unrelated containers were idle in the
same Docker VM ([`results/other-containers-during-runs.txt`](results/other-containers-during-runs.txt)).
So: medians are the figures to trust, p95/p99 carry that noise, and small
differences between runs are not findings.

Host-to-container networking on this machine added ~3 ms to a `SELECT 1`
median (3.66 ms from the host, 0.58 ms from inside the network, 300 runs each),
which is why every client runs in the network.

Sizes are decimal megabytes (10⁶ bytes) computed from byte counts, except where a
table says MiB.

Datasets are generated with a fixed seed and regenerated by [`tools/datagen.py`](tools/datagen.py)
(seed `20261013`): `saas` 6,000,000 events / 200,000 users / 2,000 tenants
with one tenant pinned to 15% of events and 0.5% of events with no tenant;
`ticks` 20,736,000 rows (100 entities × 2 metrics, every 10 s for 12 days);
`events` 10,000,000 rows over 2,000 tenants.

Latency figures are milliseconds measured by the client around execute + fetch
([`tools/bench.py`](tools/bench.py)) unless marked "server", which come from
`EXPLAIN (ANALYZE)` execution time.

## 1. Citus — `results/citus/`

Cluster: coordinator + 2 workers, `citus.shard_count = 32`, then a third worker.

### Naive distribution — `naive-attempt.log`

Each block fixes the layer above it inside a rolled-back transaction, so every
failure class surfaces. Nothing was kept (`distributed_tables = 0`).

| Attempt | Citus error |
|---|---|
| distribute `orders` first | `referenced table "tenants" must be a distributed table or a reference table` |
| reference tables, then `tenants` | `cannot create foreign key constraint since foreign keys from reference tables and local tables to distributed tables are not supported` |
| `users` with its PK and UNIQUE(email) | `cannot create constraint on "users"` |
| `events` with NULL tenants | `the partition column of table public.events cannot be NULL` |
| `AuditLog` unquoted | `relation "auditlog" does not exist`, then `column "tenantid" of relation "AuditLog" does not exist` |
| `webhook_deliveries` | `column "tenant_id" of relation "webhook_deliveries" does not exist` |

### Planned migration — `plan.json`, `plan.sql`, `migrate*.{json,log}`, `verify.tsv`

- Planner verdict: root `tenants`, key `id`; 8 tables distributed and co-located, 2 reference (`countries`, `plans`), 0 left local. Issues: `PK_WITHOUT_KEY` 8, `FK_WITHOUT_KEY` 4, `MISSING_KEY` 1, `NULL_KEY` 1, `MIXED_CASE` 1.
- **First run failed** (`migrate-attempt1-fk-failure.log`): `insert or update on table "events_102201" violates foreign key constraint "events_user_id_fkey_102201"`. Rows moved to a "system" tenant still pointed at users of real tenants, which a composite `(tenant_id, user_id)` FK rejects. The planner now clears those references in the same `UPDATE`; a test pins it.
- **Second run: 122.3 s** wall for the whole generated script (fixes, 2 reference + 8 distributed tables, FKs re-added, local data truncated), measured by the database clock around `psql -f`. All 10 tables placed in one co-location group; 11 foreign keys back; `events` 6,000,000 rows with 30,114 under the system tenant; 0 NULL tenants.

### Router vs multi-shard — `queries.json`, `plans-explain.txt`

| Query | Plan | n | p50 | p95 | p99 |
|---|---|---|---|---|---|
| one tenant, events since a date | Task Count: 1 | 200 | 3.77 | 23.02 | 77.96 |
| one tenant, events ⋈ users on (tenant, user) | Task Count: 1 | 200 | 6.53 | 41.62 | 141.52 |
| all tenants, `GROUP BY event_type` | Task Count: 32 | 20 | 677.3 | 2,787.6 | 3,769.9 |

### Co-located vs repartition join — `colocation.{json,log}`, `colocation-counts.txt`

distributed by `user_id`, Citus refuses until `citus.enable_repartition_joins = on`.

| Join | n | p50 | p95 |
|---|---|---|---|
| co-located on (tenant_id, user_id) | 7 | 1,251.7 | 2,153.8 |
| repartition join | 7 | 5,206.0 | 7,627.3 |

### Online rebalance under load — `rebalance-*`, `results/raw/rebalance-load.csv` (git-ignored, regenerated)

Load: 8 threads for 600 s, 80% one-tenant reads / 20% single-row inserts, against the coordinator. Windows cut at the job's first task start and the seventh move's success, taken from the coordinator log (`rebalance-marks.json`).

| Window | Seconds | ops/s | read p50 / p95 / p99 | write p50 / p95 / p99 | errors |
|---|---|---|---|---|---|
| before | 30.8 | 2,495 | 1.40 / 6.98 / 24.66 | 1.48 / 10.00 / 37.97 | 0 |
| during the moves | 37.1 | 2,074 | 1.66 / 9.57 / 33.57 | 2.04 / 18.89 / 54.72 | 0 |
| after | 532.0 | 1,548 | 2.09 / 11.60 / 42.87 | 3.57 / 23.09 / 66.05 | 0 |

- 977,368 operations, 0 errors. Every acknowledged write is present: `events` = 6,256,396 + 195,543 = **6,451,939**.
- 7 shard-group moves plus reference-table replication took **37.1 s**.
- The "after" window is slower than "during" while nothing was moving; host load rose from 11.6 to 31.1 over the run, so I do not attribute it to the cluster.
- **The eighth move failed** — see Failures in the README. After removing the stale cleanup rows (`rebalance-repair.log`) it completed in **5.3 s**.
- Earlier attempts are kept: `rebalance-attempt1-no-replica-identity.log` (a table without a primary key blocked the rebalancer), `rebalance-attempt2-harness-bug-summary.json` (my harness reused insert ids; superseded).

### Size skew and the whale — `skew-before.tsv`, `isolate*.log`, `skew-after.tsv`, `skew-base-cost-zero.txt`

20,736,000 ticks, loaded twice: once per primary-key order, 1-day chunks.

| time-led PK + index (entity_id, metric, ts) | 1,249.7 MB | 1,979.6 MB | 1.58 | index build 19.8 s |

### Insert-only vacuum — `vacuum.log`

5,000,000 rows into a plain table with autovacuum off, then one indexed query
(entity 42 since 2026-07-20, 33,584 rows).

| State | all-visible pages | Plan | Heap blocks read | Execution |
|---|---|---|---|---|
| never vacuumed | 0 of 36,765 | bitmap heap scan | 24,695 | 87.97 ms |
| after `VACUUM` | 36,765 of 36,765 | index-only scan, heap fetches 0 | 0 | 2.55 ms |

Insert-triggered autovacuum, adding 500,000 rows (~10%) and waiting 20 s:
default `autovacuum_vacuum_insert_scale_factor = 0.2` → not triggered
(`n_ins_since_vacuum` 500,000); per-table `0.01` with threshold 10,000 →
triggered, `n_ins_since_vacuum` 0, all 44,118 pages all-visible.

## 4. Same data, four engines — `results/compare/`

10,000,000 rows from `events_by_ts.csv` (the `events` dataset sorted by time),
one engine at a time on the same VM, row counts verified identical
(`COPY 10000000` ×3, `ch-rowcount-check.txt`). Postgres-family servers had
`shared_buffers = 2GB`.

| Engine and layout | Load | rows/s | On disk |
|---|---|---|---|
| PostgreSQL 17, monthly range partitions + B-tree (tenant_id, ts) | COPY 13.8 s + index 9.4 s | 724,638 | 1,157.7 MB |
| Citus 14.2 columnar, no index | COPY 8.7 s | 1,149,425 | 123.6 MB |
| TimescaleDB 2.30, 7-day chunks, columnstore segmented by tenant | COPY 30.2 s + compress 20.7 s | 331,126 | 139.5 MB |
